# Сервис сверки событий финансовых операций в распределённой системе

**Репозиторий:** [github.com/alexsavchenko1/ledger-guard](https://github.com/alexsavchenko1/ledger-guard)

## О проекте

Я разработал сервис, который собирает события одной финансовой операции из нескольких систем и проверяет, что вся цепочка обработки сошлась.

Идею проекта я взял из своих рабочих задач в Т-Банке. Там одна операция часто проходит через несколько сервисов, и потом приходится разбираться, почему цепочка не сошлась: событие потерялось, пришло дважды, оказалось записано не в том порядке или содержит другие данные. В Ledger Guard я взял эту механику за основу и собрал отдельный учебный проект, который такие расхождения находит.

Конкретную рабочую систему я сюда не переносил. Сценарий, данные и реализацию придумал отдельно, но саму задачу взял из практики.

В качестве примера используется пополнение инвестиционного счёта. Полная операция состоит из четырёх событий:

1. `DEPOSIT_CREATED` - создано пополнение;
2. `MONEY_DEBITED` - деньги списаны со счёта клиента;
3. `TRANSFER_COMPLETED` - перевод выполнен;
4. `FUNDS_CREDITED` - средства зачислены на инвестиционный счёт.

После каждого нового события сервис сохраняет его, загружает всё текущее состояние операции и заново выполняет сверку.

## Мой вклад

В рамках проекта я:

- спроектировал доменную модель финансовой операции и набор статусов сверки;
- реализовал правила проверки полноты, суммы, клиента, валюты, источника и порядка событий;
- добавил обработку точных дублей и конфликтующих событий с одинаковым `event_id`;
- реализовал чтение и валидацию событий из JSON;
- подключил PostgreSQL для хранения событий и результатов сверки;
- реализовал Kafka consumer с ручным подтверждением offset;
- добавил DLQ для сообщений, которые невозможно разобрать или провалидировать;
- реализовал идемпотентное сохранение точных дублей;
- добавил FastAPI для получения результата и синхронного запуска сверки;
- подготовил Docker Compose для запуска Kafka, PostgreSQL, consumer и API одной командой;
- добавил автоматическое создание Kafka topics и сохранение данных в Docker volumes;

## Сценарий работы

Общая цепочка выглядит так:

```text
Producer -> Apache Kafka -> Python consumer ->
сохраняет событие в PostgreSQL ->
запускает Reconciliation Engine ->
сохраняет результат сверки в PostgreSQL

Клиент -> FastAPI -> получает сохранённый результат

Некорректное сообщение -> operation-events-dlq
```

Каждое событие содержит:

- уникальный идентификатор события;
- идентификатор операции;
- тип события;
- источник;
- клиента;
- сумму;
- валюту;
- время возникновения.

Пример:

```json
{
  "event_id": "event-1",
  "operation_id": "operation-1",
  "event_type": "DEPOSIT_CREATED",
  "source": "funding_service",
  "client_id": "client-1",
  "amount": "15000.00",
  "currency": "RUB",
  "occurred_at": "2026-07-24T12:00:00+00:00"
}
```

После поступления сообщения consumer:

1. декодирует JSON;
2. проверяет обязательные поля;
3. преобразует данные в доменную модель;
4. сохраняет событие в PostgreSQL;
5. загружает все события с тем же `operation_id`;
6. запускает сверку;
7. сохраняет актуальный статус операции;
8. подтверждает Kafka offset.

## Логика сверки

Сервис проверяет:

- получены ли все четыре обязательных события;
- относятся ли они к одной операции;
- совпадают ли клиент и валюта;
- совпадает ли сумма;
- пришло ли каждое событие от ожидаемой системы;
- соблюдён ли временной порядок этапов;
- нет ли повторного события одного типа;
- нет ли событий с одинаковым `event_id`, но разными данными.

Операция получает один из статусов:

| Статус | Значение |
|---|---|
| `PENDING` | цепочка ещё не собрана полностью |
| `MATCHED` | все события получены, данные совпадают |
| `AMOUNT_MISMATCH` | в событиях отличаются суммы |
| `DATA_MISMATCH` | найдено другое расхождение |
| `INVALID_SEQUENCE` | нарушен временной порядок этапов |

Пока получена только часть цепочки, операция остаётся в статусе `PENDING`. После прихода нового события сверка выполняется заново, поэтому статус постепенно меняется вместе с накоплением данных.

## Повторная доставка и идемпотентность

Kafka использует модель доставки, при которой одно сообщение может быть получено повторно. Поэтому consumer не должен создавать новую запись при каждой повторной доставке.

В таблице событий используется ограничение уникальности по полному набору данных события. Если consumer получает точную копию уже сохранённого сообщения, новая строка не создаётся. После этого сервис всё равно загружает текущее состояние операции и повторно получает тот же результат сверки.

При этом событие с тем же `event_id`, но изменёнными данными не отбрасывается как обычный дубль. Оно сохраняется, а движок сверки возвращает `DATA_MISMATCH`.

Kafka offset подтверждается только после успешного сохранения события и результата сверки. Если обработка не завершилась, сообщение может быть доставлено повторно.

## Работа с некорректными сообщениями

Сообщение отправляется в `operation-events-dlq`, если:

- JSON невозможно разобрать;
- отсутствует обязательное поле;
- передан неизвестный тип события;
- значение нельзя преобразовать в нужный тип;
- событие не проходит доменную валидацию.

В DLQ сохраняются:

- исходное сообщение;
- тип ошибки;
- текст ошибки;
- исходный topic;
- partition;
- offset.

После успешной отправки в DLQ offset исходного сообщения подтверждается, поэтому одно и то же некорректное сообщение не блокирует основной consumer бесконечно.

## Хранение данных

В PostgreSQL используются две основные таблицы.

`operation_events` хранит все полученные события. По `operation_id` consumer загружает текущее состояние операции перед каждой новой сверкой.

`reconciliation_results` хранит последний рассчитанный статус операции, количество учтённых событий и время проверки. При повторной сверке запись обновляется через upsert.

Такой подход позволяет отдельно хранить историю входящих событий и актуальный итог сверки.

## API и CLI

FastAPI предоставляет два endpoint:

```http
GET /results/{operation_id}
POST /reconcile
```

`GET /results/{operation_id}` возвращает последний сохранённый результат.

`POST /reconcile` принимает массив событий, запускает тот же движок напрямую, без Kafka, и сохраняет итог в PostgreSQL. Этот endpoint нужен для быстрой проверки логики и ручного тестирования.

Также в проекте остался первоначальный CLI-режим. Он читает события из JSON-файла и позволяет запускать доменную логику без Kafka и PostgreSQL.

## Запуск через Docker Compose

Вся система запускается одной командой:

```bash
docker compose up -d --build
```

Docker Compose поднимает:

- PostgreSQL;
- Apache Kafka в KRaft-режиме;
- одноразовый контейнер для подготовки Kafka volume;
- одноразовый контейнер для создания topics;
- Python consumer;
- FastAPI.

Для Kafka и PostgreSQL используются Docker volumes, поэтому данные сохраняются после обычного `docker compose down`.

Конфигурация рассчитана на локальную демонстрацию. Внешний Kafka listener доступен через `localhost:9092`, PostgreSQL - через `localhost:5433`, API - через `localhost:8000`.

## Ограничения

Проект представляет собой локальный инженерный прототип.

В текущей версии используется один Kafka broker, одна partition и один consumer. В проекте нет авторизации, метрик, распределённой трассировки и отдельной системы миграций базы данных.

Я сознательно не добавлял эти компоненты только ради расширения списка технологий. Основной целью было собрать понятную и законченную цепочку обработки события без искусственного усложнения архитектуры.
